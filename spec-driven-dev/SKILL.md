# Spec Driven Dev — AI 项目认知系统 v2.0

## 核心理念

> **Spec 是 AI Agent 的"项目记忆芯片"。新会话打开，读完 Spec，5 秒恢复全部上下文。**

| 痛点 | 本技能的解决方案 |
|------|------------------|
| AI 开新会话找不到北 | `spec.md` 作为唯一入口，30 秒理解全局 |
| Token 浪费在无关上下文上 | 网关模式——主文档只做路由，子文档按需加载 |
| 用户描述不清需求 | 引导式对话，≤3 轮收敛到可执行方案 |
| AI 做完改动忘了更新文档 | 三级维护协议，硬性约束什么时候必须更新 |
| 各 AI 对同一项目理解不一致 | Spec 就是 Source of Truth，谁来都读同一份 |

---

## 何时使用

满足以下**任一**条件时触发：

- 用户想开发新系统、新功能、新项目
- 用户说"帮我梳理需求"、"帮我写 spec"、"帮我做技术规范"
- 用户描述了一个模糊的想法，需要拆解为可执行方案
- 已有项目需要重新梳理架构和规范
- AI 在新会话中打开项目，需要恢复上下文

---

## ⚠️ 执行前必读

1. **先检查 `project-manifest.md`**：如果项目根目录下存在此文件，先阅读它，它会指引你到 `specs/spec.md`。
2. **再检查 `specs/spec.md`**：如果存在，先阅读它了解项目全貌，再与用户沟通增量需求。
3. **不要重复造轮子**：如果用户提到的功能在已有 spec 中已有定义，提醒用户该功能已存在。
4. 所有 spec 文档存放在 `specs/` 目录下。

## 文档体系架构（API 网关模式）

```
项目根目录/
├── project-manifest.md          ← 301 重定向（≤5 行，指向 spec.md）
├── specs/
│   ├── spec.md                  ← 🌐 网关入口（≤1000 tokens）
│   ├── spec-database.md         ← 📊 数据模型详情（按需加载）
│   ├── spec-api.md              ← 🔌 接口设计详情（按需加载）
│   ├── spec-ui.md               ← 🎨 页面与交互详情（按需加载）
│   ├── spec-design.md           ← 🎯 Design Tokens（按需加载）
│   └── spec-logic.md            ← ⚙️ 核心业务流程（按需加载）
```

**规则：**
- `spec.md` 是**唯一入口**，严格控制在 **1000 tokens** 以内
- 子文档每个控制在 **1000-2000 tokens**
- AI 只在需要修改对应模块时才加载对应子文档（Lazy Loading）

## 工作流程（共 4 个阶段）

### 阶段一：需求探索（≤3 轮对话）

**你的角色**：产品经理 + 运营专家

#### 第 1 轮：定位与核心问题

向用户提出以下问题（合并为一次提问）：

1. **一句话定位**：这个系统用一句话怎么描述？
2. **核心问题**：它解决了什么痛点？
3. **目标用户**：谁在用？使用场景是什么？
4. **已有资源**：有参考产品、设计稿、或相关代码吗？

> 💡 如果用户回答简略，用"比如说…"给出 2-3 个具体场景帮助发散。

#### 第 2 轮：场景与边界

1. 列出 **3-5 个核心 User Story**（"作为 XX，我想要 XX，以便 XX"）
2. **MVP 范围**：这个版本做什么 / 不做什么
3. **非功能性需求**：性能、安全、数据量

#### 第 3 轮：确认理解

用结构化摘要确认：产品定位、目标用户、核心场景、MVP 范围、特殊约束。

**用户确认后 → 进入阶段二。**

---

### 阶段二：技术决策

**你的角色**：架构师 + 全栈工程师

#### 2.1 技术栈选型

**直接给出推荐并说明理由**（不要让用户自己选）：
- 编程语言 & 框架
- 数据库
- 基础设施 & 部署方式
- 第三方服务

#### 2.2 模块划分

将系统拆解为功能独立的模块，每个包含：

| 模块名 | 核心职责（一句话） | 对外接口 | 依赖 |
|--------|-------------------|---------|------|
| ... | ... | ... | ... |

#### 2.3 目录结构设计

设计项目文件目录，**每个目录必须标注设计意图和修改规则**。

**用户确认后 → 进入阶段三。**

---

### 阶段三：Spec 文档生成

**你的角色**：技术文档专家

根据前两个阶段的结果，生成以下文档：

#### 3.1 生成 `project-manifest.md`

- 路径：`{项目根目录}/project-manifest.md`
- 模板：[project-manifest-template.md](references/project-manifest-template.md)
- 要求：**≤5 行**，纯跳板

#### 3.2 生成主入口 `spec.md`

- 路径：`{项目根目录}/specs/spec.md`
- 模板：[spec-template.md](references/spec-template.md)
- 要求：**≤1000 tokens**，只包含身份卡 + 全局约束 + 子文档路由

#### 3.3 按需生成子文档

| 条件 | 子文档 | 文件名 | 模板 |
|------|--------|--------|------|
| 有前端 UI | UI 设计规范 | `spec-design.md` | [spec-design-template.md](references/spec-design-template.md) |
| 数据模型 ≥ 3 张表 | 数据库设计 | `spec-database.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| API ≥ 5 个接口 | 接口设计 | `spec-api.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| 前端 ≥ 3 个页面 | UI 页面详情 | `spec-ui.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| 有复杂业务状态机 | 业务逻辑 | `spec-logic.md` | [spec-sub-template.md](references/spec-sub-template.md) |

---

### 阶段四：验收确认

1. 列出所有生成的文件及路径
2. 逐个 highlight 关键决策点
3. 用户确认后定稿

## 三级维护协议（Maintenance Protocol）

> **这是硬性规约。AI 在任何开发过程中都必须遵守。**

### 🔴 必须先改 Spec 再改代码（Design-First）

以下动作**必须**先在对应 `specs/*.md` 中记录 Proposed Changes，用户确认后才动代码：

- 新增数据库表或实体
- 新增页面路由
- 引入新的第三方依赖
- 修改全局 Design Tokens（配色、字体、圆角等）

### 🟡 代码完成后同步更新 Spec

以下动作在代码完成后，**必须**回头更新对应 `specs/*.md`：

- 修改现有 API 的入参/出参
- 调整核心业务流程
- 新增/修改 User Story

### 🟢 无需更新 Spec

以下动作**不需要**更新 Spec：

- 纯 CSS 样式微调（不涉及 Design Tokens）
- Bug 修复
- 代码重构但不改接口行为
- 日志/注释/文档修正

### 兜底安全网

在 `code-commit` / `code-submit` 阶段，检查 `git diff --name-only`：
- 如果 `entity/` 或 `migration/` 变了，但 `specs/spec-database.md` 没变 → 拦截并要求补文档
- 如果 `pages/` 或 `router` 变了，但 `specs/spec-ui.md` 没变 → 拦截并要求补文档

## 迭代需求处理

当项目已有 spec 文档，用户提出新需求时：

1. **先读 `specs/spec.md`**：了解项目全局
2. **按需加载子文档**：只读与新需求相关的子文档
3. **确认增量范围**：新需求影响哪些模块？
4. **按照三级维护协议更新 spec**
5. **在 `spec.md` 底部的"开发日志"中记录变更**

> ⚠️ **绝对不要跳过步骤 1-2 直接开始开发。**

---

## 边界情况

| 场景 | 处理方式 |
|------|---------|
| 用户只有模糊想法 | 从"你想解决什么问题？"开始引导 |
| 用户拒绝写 spec | 温和提醒价值，若坚持则尊重 |
| 需求极简（单个小功能） | 只生成精简的 `spec.md`，跳过子文档 |
| 已有项目没有 spec | 先扫描项目结构，反向生成 `spec.md` |

## 输出质量检查

- [ ] `spec.md` ≤ 1000 tokens
- [ ] 每个子文档 ≤ 2000 tokens
- [ ] 全部使用表格/列表/编号步骤，无叙述体散文
- [ ] 全局约束已定义（技术栈红线、编码规范）
- [ ] `project-manifest.md` ≤ 5 行
- [ ] 子文档链接正确且文件已创建
