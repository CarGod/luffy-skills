# Spec Driven Dev — 规范驱动开发

## 何时使用此 Skill

当满足以下**任一**条件时使用：

- 用户想开发一个新系统、新功能、新项目
- 用户说"帮我梳理需求"、"帮我写 spec"、"帮我做技术规范"
- 用户描述了一个模糊的想法，需要被拆解为可执行的技术方案
- 已有项目需要重新梳理架构和规范
- 用户希望在开始 Vibe Coding 前做好规划

此 Skill **不做**界面设计或概念发散。本 Skill 聚焦于**从需求到可执行的工程规范**。

---

## 核心理念

> **Spec Markdown 是 AI Agent 编程的"单一真理来源（Source of Truth）"。**
> 给 AI 一份清晰的 Spec，比靠"感觉"写 Prompt 要靠谱一万倍。

本 Skill 解决 Vibe Coding 五大痛点：

| 痛点 | 解决方案 |
|------|---------|
| 用户描述不清需求 | 引导式需求对话，分阶段收敛 |
| 技术栈混乱 | 在 spec 中显式约束技术选型 |
| 缺乏模块化设计 | 强制定义模块划分和目录职责 |
| 重复造轮子 | Project Manifest 维护全局文件索引 |
| 上下文窗口溢出 | 主文档 + 子文档树，新窗口读 manifest 即可恢复 |

---

## ⚠️ 执行前必读

1. 如果项目根目录下已有 `spec.md` 或 `project-manifest.md`，**必须先阅读它们**，了解项目现状后再与用户沟通增量需求。
2. 如果用户提到的功能在已有 spec 或 manifest 中已有定义，**提醒用户该功能已存在**，避免重复开发。
3. 所有 spec 文档默认存放在项目根目录的 `specs/` 目录下。

## 工作流程（共 4 个阶段）

### 阶段一：需求探索（Discovery）

**你的角色**：产品经理 + 运营专家

目标是用**不超过 3 轮对话**，帮用户从模糊想法收敛到清晰需求。

#### 第 1 轮：定位与核心问题

向用户提出以下问题（可合并为一次提问，不要逐个问）：

1. **一句话定位**：这个系统/功能用一句话怎么描述？
2. **核心问题**：它解决了用户的什么痛点？没有它会怎样？
3. **目标用户**：谁在用？他们的技术水平和使用场景是什么？
4. **已有资源**：有没有现成的参考产品、设计稿、或相关代码？

> 💡 **技巧**：如果用户回答过于简略，用"比如说…"的方式给出 2-3 个具体场景让用户选择或补充。

#### 第 2 轮：场景与边界

基于第 1 轮回答，展开具体场景：

1. **列出 3-5 个核心使用场景**（User Story 格式："作为 XX，我想要 XX，以便 XX"）供用户确认
2. **边界界定**："这个版本做什么 / 不做什么"（MVP 范围）
3. **非功能性需求**：性能、安全、数据量预估等

#### 第 3 轮：确认理解

用结构化摘要向用户确认：
- 产品定位
- 目标用户
- 核心场景列表
- MVP 范围（做 / 不做）
- 特殊约束

**用户确认后，进入阶段二。**

---

### 阶段二：技术决策（Technical Decision）

**你的角色**：架构师 + 全栈工程师

#### 2.1 技术栈选型

基于需求场景，**给出推荐并说明理由**，而非让用户自己选。包括：
- 编程语言 & 框架（前端 / 后端 / 移动端）
- 数据库（关系型 / NoSQL / 缓存）
- 基础设施（部署方式、CI/CD）
- 第三方服务（支付、存储、消息队列等）

#### 2.2 模块划分

将系统拆解为**功能独立、职责清晰的模块**，每个模块包含：
- 模块名称
- 核心职责（一句话）
- 对外接口概要
- 与其他模块的依赖关系

#### 2.3 目录结构设计

设计项目的文件目录结构，**明确每个目录和关键文件的职责**。这是后续 `project-manifest.md` 的基础。

#### 2.4 与用户确认技术方案

将技术选型和模块划分以表格或清单的形式呈现给用户确认。

**用户确认后，进入阶段三。**

---

### 阶段三：Spec 文档生成（Spec Generation）

**你的角色**：技术文档专家

根据前两个阶段的沟通结果，生成以下文档体系：

#### 3.1 生成主文档 `spec.md`

- 存放路径：`{项目根目录}/specs/spec.md`
- **Token 预算**：控制在 **1000-3000 Tokens**（约 100-300 行）
- 严格按照 [spec-template.md](references/spec-template.md) 模板生成
- 复杂模块只写概要，通过链接指向子文档

#### 3.2 按需拆分子文档

根据以下规则判断是否需要拆分子文档：

| 条件 | 拆分的子文档 | 文件名 | 模板 |
|------|------------|--------|------|
| 有前端 UI（任何含前端的项目） | UI 设计规范 | `spec-design.md` | [spec-design-template.md](references/spec-design-template.md) |
| 数据模型 ≥ 3 张表 | 数据库设计详情 | `spec-database.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| API ≥ 5 个接口 | 接口设计详情 | `spec-api.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| 前端 ≥ 3 个页面/视图 | UI 页面详情 | `spec-ui.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| 有复杂业务状态机 | 业务逻辑详情 | `spec-logic.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| 需要第三方集成 | 集成方案详情 | `spec-integration.md` | [spec-sub-template.md](references/spec-sub-template.md) |
| 有独立的部署需求 | 部署运维方案 | `spec-devops.md` | [spec-sub-template.md](references/spec-sub-template.md) |

- 子文档存放路径：`{项目根目录}/specs/spec-{模块名}.md`
- `spec-design.md` 严格按照 [spec-design-template.md](references/spec-design-template.md) 生成
- 其他子文档严格按照 [spec-sub-template.md](references/spec-sub-template.md) 生成
- 每个子文档也应控制在 **1000-3000 Tokens**

> 💡 **`spec-design.md` 特别说明**：此文档定义项目的 Design Tokens（设计令牌），包括色彩体系、字体排版、间距圆角、阴影、动效和组件视觉规范。对于已有项目，应从 CSS 变量 / 样式文件中提取实际值；对于新项目，应在此文档中先定义好设计系统再开始编码。AI 在实现任何新页面或组件时，必须参照此文档保持视觉一致性。

#### 3.3 主文档引用子文档的方式

在 `spec.md` 的对应模块章节中，使用以下格式引用子文档：

```markdown
## 4. 数据模型

本系统使用 PostgreSQL，共包含 5 张核心表。

> 📖 **详细设计**：请查阅 [spec-database.md](./spec-database.md)，包含完整的表结构定义、索引策略和数据关系图。

### 核心表概览

| 表名 | 职责 | 关键字段 |
|------|------|---------|
| users | 用户主表 | id, name, role |
| orders | 订单表 | id, user_id, status |
| ... | ... | ... |
```

#### 3.4 生成 Project Manifest

- 存放路径：`{项目根目录}/project-manifest.md`
- 严格按照 [project-manifest-template.md](references/project-manifest-template.md) 模板生成
- **此文件是 AI 在新对话窗口中恢复项目上下文的入口**

---

### 阶段四：验收确认（Review & Confirm）

将生成的文档以清单形式呈现给用户：

1. 列出所有生成的文件及其路径
2. 逐个 highlight 每个文档的关键决策点
3. 询问用户是否有需要修改的部分
4. 根据反馈修订文档
5. 确认最终版本

---

## 迭代需求的处理

当项目已有 spec 文档，用户提出新需求时：

1. **先读 `project-manifest.md`**：了解项目全貌
2. **再读相关的 spec 文档**：了解已有设计
3. **与用户确认增量范围**：新需求影响哪些模块？
4. **更新 spec 文档**：修改受影响的 spec 文件，标注变更内容
5. **更新 manifest**：在 project-manifest.md 的变更日志中记录本次迭代

> ⚠️ **绝对不要跳过步骤 1-2 直接开始开发。** 这是防止重复造轮子和架构腐化的关键。

## 树状文档结构示例

一个典型的 spec 文档体系如下：

```
my-project/
├── project-manifest.md          # 🧭 项目全局清单（AI 入口）
├── specs/
│   ├── spec.md                  # 📋 主规范文档（总控）
│   ├── spec-database.md         # 💾 数据库设计
│   ├── spec-api.md              # 🔌 API 接口设计
│   ├── spec-ui.md               # 🎨 前端页面设计
│   ├── spec-logic.md            # ⚙️ 核心业务逻辑
│   └── spec-integration.md      # 🔗 第三方集成
├── src/
│   ├── ...
```

## 输出质量检查清单

生成文档后，用以下清单自检：

- [ ] 每个 spec 文档都在 1000-3000 Tokens 之间
- [ ] 主文档中的子文档引用链接正确且对应文件已创建
- [ ] 技术栈选型有明确理由，不是随意选择
- [ ] 模块划分职责单一，没有"万能模块"
- [ ] 目录结构中每个目录都有明确职责说明
- [ ] project-manifest.md 中的文件列表与实际项目结构一致
- [ ] 验收标准具体且可测试，不是"系统正常运行"这样的空话
- [ ] 阶段任务拆解可操作，每个阶段有明确的产出物

## 边界情况处理

### 用户只有一个很模糊的想法
→ 从 "你想解决什么问题？" 开始，用具体案例帮助用户发散和聚焦。

### 用户要求直接写代码，不想写 spec
→ 温和提醒 spec 的价值："项目越大，没有 spec 的代价就越高。先花 10 分钟理清需求，能在后面节省 10 小时的返工。" 如果用户坚持，尊重用户意愿。

### 需求非常简单（单个小功能）
→ 不需要完整的文档体系。只生成一个精简的 `spec.md`，跳过子文档和 manifest。

### 已有项目没有 spec
→ 先扫描项目结构，生成 `project-manifest.md` 作为起点，然后再针对新需求生成 spec。
